①

ระบบนี้คืออะไร

Sangwijit ERP Web Portal = หน้าเว็บ (Frontend) ชั้นเดียวที่ครอบอยู่บน Microsoft Dynamics 365 Business Central (BC365) — ระบบบัญชี/คลัง/ขาย/ซื้อ ตัวจริงที่อยู่เบื้องหลัง

ธุรกิจ: กลุ่มแสงวิจิตร — จำหน่ายเครื่องใช้ไฟฟ้า (ยอดขาย 450M+/ปี) ทำทั้ง ค้าปลีก ค้าส่ง ส่งออก ศูนย์บริการ/ซ่อม

ทำไมต้องมี Portal: BC365 มาตรฐานใช้ยากสำหรับพนักงานหน้างาน · Portal ทำหน้าจอที่ง่ายกว่า + workflow ที่ตรงกับวิธีทำงานจริงของบริษัท (คิวงาน, waterfall เกลี่ยของ, เคลม, มัดจำ ฯลฯ) แล้วยิงคำสั่งไป BC365 ให้ลงบัญชีจริง

ตอนนี้อยู่ช่วง: ออกแบบ mockup หน้าจอ (HTML) · Phase 1 ~34 หน้าจอสำหรับโมดูล Run-ASAP · ยังไม่ได้ต่อ BC365 จริง

Portal ทำอะไร

  • หน้าจอที่ง่าย + คิวงาน + workflow ตามวิธีทำงานจริง
  • ตรวจสิทธิ์ (ใครทำอะไรได้), Maker≠Checker
  • รวบข้อมูลแล้ว "ยิง" ไป BC ให้ Post
  • Retry/Queue เมื่อ BC ช้า

Portal ไม่ทำ (BC ทำ)

  • ไม่มีฐานข้อมูลของตัวเอง — ดึงจาก BC ทั้งหมด
  • ไม่ Post บัญชี/ตัดสต๊อกเอง
  • ไม่ออกเลขที่เอกสารเอง (ยกเว้น sub-series ที่ตกลงไว้)
  • ไม่คิดราคา/สถานะเอง — มาจาก BC

💡 ในผัง Flow จะเห็น 2 เลนเสมอ: Web Portal (บน) กับ BC365 (ล่าง) — จุดที่เขียนว่า “⚡ Function Post” คือจังหวะที่ BC ลงบัญชีจริง · งานบัญชีปลายน้ำ (รับ-จ่าย-GL-ภาษี) หลายผังอยู่เลน BC ล้วน = Portal เป็นแค่ปุ่มกด

กฎธุรกิจหลัก (จำ 6 ข้อนี้)

ผิดข้อไหน = mockup ผิด
🧮 VAT Golden Rule
ส่วนลดหักก่อน VAT เสมอ (ไม่ใช่หลัง)
🎁 Rebate ≠ Discount
ส่วนลด = ลดราคาก่อนขาย · Rebate = เงินคืนจาก vendor หลังขาย (คนละเรื่อง อย่าปน)
📗 Dual-Book
ใบตั้งหนี้เจ้าหนี้ทุกใบติด Entity Tag (1/2/3/novat) แยกสมุดบัญชี · ⏸️ defer นอก scope SWT (FI-13/CF-2.8)
✍️ Maker ≠ Checker
คนสร้างเอกสาร ห้าม อนุมัติงานตัวเอง — ทุกจุดที่มีอนุมัติ
🔐 อนุมัติจุดเดียว
ทุกการอนุมัติวิ่งผ่าน CF-2.6 Approval Matrix (ทั้งขาย SL-F1 + ซื้อ PO)
🏦 Portal = UI
ไม่มี DB เอง · ไม่ Post นอก BC · เลข/สถานะ/ราคา = BC เจ้าของ

7 สายหลัก (เอกสารไหลข้ามโมดูลยังไง)

คลิกกล่องเปิดหน้าจริง
1 · ขายOrder-to-Cash
SL-1 ใบเสนอราคา→ SL-2 ใบจอง/จองสต็อก→ SL-3 ใบรับมัดจำ→ SL-4 บิลขาย/ใบกำกับภาษี→ WH-2 ใบเบิก/ส่งของ→ FI-1 รับชำระลูกหนี้
2 · ซื้อProcure-to-Pay
PO-1 ใบขอซื้อ→ PO-4 ใบสั่งซื้อ→ WH-1 ใบรับสินค้า→ PO-6 ใบตั้งหนี้เจ้าหนี้→ FI-2 จ่ายชำระเจ้าหนี้
3 · ลดหนี้ขายคืน/เคลม
SL-4 บิลขายต้นทาง→ SL-CN ใบลดหนี้ขาย→ FI-1Q จับคู่/คืนเงิน
4 · โอนคลังIn-Transit
WH-3R ใบขอโอน→ WH-3 ใบโอนสินค้า→ 🚚 In-Transit (ระหว่างขนส่ง)→ WH-1 รับปลายทาง
5 · ภาษีหัก ณ ที่จ่ายWHT
FI-2 จ่าย + หักภาษี→ FI-12 ออกหนังสือรับรอง + ภ.ง.ด.3/53 (จุดเดียว)
6 · คลังปฏิบัติการKitchen Rail + Waterfall
WH-Q1 คิวรับสินค้า· WH-Q2 คิวเบิกสินค้า· เกลี่ยของ: เบิก→โอน→ซื้อ
7 · บริการService Ops
SV-1 ใบรับงานบริการ→ SV-2 มอบหมายช่าง→ SV-3 เบิกอะไหล่→ SV-4 ปิดงาน/ตรวจรับ→ CLM ใบเคลมผู้ขาย
⑤

สถานะเอกสาร + สีมาตรฐาน

ทุกเอกสารเดินตาม lifecycle นี้

รูปแบบทั่วไป: Draft → รออนุมัติ → อนุมัติ → Posted (ลง BC) → ปิดงาน · ถ้าปฏิเสธ → กลับ Draft

Draft — ร่าง รออนุมัติ อนุมัติแล้ว รอ Post Posted (ลง BC แล้ว) ยกเลิก นัดล่วงหน้า

💡 UI เปลี่ยนตามสถานะเสมอ (Status-Driven): สี badge + ปุ่มที่กดได้ (ActionBar) เปลี่ยนตามว่าเอกสารอยู่สถานะไหน + คนดูมีสิทธิ์อะไร

SC8 แผง Serial number (สแกน/นำเข้า CSV)
SC9 ราคา+โปรฯ อัตโนมัติ (อ่านทุกหน้าขาย)
SC10 ค้นหาผู้ขาย (Vendor + WHT rate)

อภิธานศัพท์ (ศัพท์ที่เจอบ่อย)

BC365 = Dynamics 365 Business Central (ระบบบัญชีตัวจริง)
Post = ลงบัญชี/ตัดสต๊อกจริงใน BC (ย้อนไม่ได้ ต้องออกใบกลับ)
PR / PO = ใบขอซื้อ / ใบสั่งซื้อ
GRN = ใบรับสินค้า (Goods Receipt)
SO = ใบสั่งขาย (ในระบบนี้ ใบจอง = SO)
AR / AP = ลูกหนี้ / เจ้าหนี้
CN = ใบลดหนี้ (Credit Note/Memo)
WHT = ภาษีหัก ณ ที่จ่าย (ภ.ง.ด.3/53)
VAT = ภาษีมูลค่าเพิ่ม 7%
3-Way Match = จับคู่ ใบสั่งซื้อ = ใบรับ = ใบวางบิล ก่อนจ่าย
In-Transit = ของกำลังโอนระหว่างคลัง (ยังไม่เข้าปลายทาง)
Kitchen Rail = คิวรวมงานคลังตามทิศ (รับ/เบิก/นับ)
Waterfall = ของไม่พอ → เกลี่ย เบิก→โอน→ซื้อ ตามลำดับ
Maker≠Checker = คนทำ ≠ คนอนุมัติ
Dual-Book = ติด Entity Tag แยกสมุดบัญชีต่อกิจการ (⏸️ defer · นอก scope SWT ปัจจุบัน — FI-13/CF-2.8)
Rebate = เงินคืนจาก vendor หลังขาย (≠ ส่วนลด)
RBAC = สิทธิ์ตามบทบาท (ใครทำอะไรได้)
รหัสโมดูล sl=ขาย po=ซื้อ wh=คลัง fi=การเงิน sv=บริการ pm=โปรฯ md=ข้อมูลหลัก cf=ตั้งค่า
